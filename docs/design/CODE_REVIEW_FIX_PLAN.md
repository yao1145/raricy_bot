# 代码审查问题修复计划

日期：2026-09-21。状态：**待实施**。

本计划对应本次代码审查确认的四项问题，记录目标、实施顺序、回归测试与交付要求。
本文描述的是拟议行为，不替代现行 [内部契约](INTERFACES.md) 或
[决策记录](DESIGN_DECISIONS.md)；完成实现和验证后再同步现行契约。

## 1. 范围、依据与实施顺序

| 顺序 | 优先级 | 问题 | 预期结果 |
|---|---|---|---|
| 1 | P1 | 关闭或清空记忆后，在途自动提取仍可写入 | 隐私操作成功后，先前提取不能继续提交 |
| 2 | P1 | 普通模型 400/404 永久禁用工具能力 | 单次请求错误不影响后续请求的工具能力 |
| 3 | P2 | 发送成功后取消任务，配额预留泄漏 | 已确认发送的预留恰好结算一次 |
| 4 | P2 | 同一会话的等待请求占满工作器 | 同会话有序串行，不占用其他会话可用的执行槽位 |

审查基线：当时全套离线测试 **2932 项通过**，四项问题由额外离线探针复现。
该数字不是本计划实施后的验证结果，也不代表真实站点验收。

前三项先分别修复和验证，最后调整共享调度接口。每项保持可独立审查和回退，
不将四项改动混入一次无法区分责任的大规模重构。

约束与非目标：

- 不启动机器人、不访问真实站点或模型 API、不部署、不自动提交。
- 预计不新增依赖、不迁移 SQLite 表、不更改记忆 Markdown 格式。
- 保持消息去重、历史提交、权限门禁、公开投影保护、日志脱敏与发文不确定结果策略。
- 不顺带重写评论或发文子系统；共享接口的消费者必须核对并同步。
- 不把四项修复写成历史线上静默事件已经定案；事件因果仍按事件档案中的证据判断。

## 2. 记忆授权：提交时原子复核

### 2.1 问题与代码入口

[MemoryController](../../src/raricy_bot/memory/controller.py) 的 `_auto_capture` 在调用
撰写器之前检查自动提取开关，等待模型返回后直接提交。聊天与记忆命令在
[App](../../src/raricy_bot/app.py) 中使用两个独立的 `WorkerPool`，会话锁不共享。
[MemoryService](../../src/raricy_bot/memory/service.py) 的写锁只保护单次 mutation，
无法阻止等待模型期间完成的隐私操作被迟到结果越过。

已复现 `/memory off` 成功后仍新增条目，以及 `/memory clear` 成功后迟到提取重新写入。
相关约定：INTERFACES §30–§34、D-59、D-60、D-67、D-80、D-100、D-102。

### 2.2 目标行为

`/memory off`、`/memory auto off` 或 `/memory clear` 成功后，此前已经开始的自动提取
不得再写入。关闭后重新开启，也不得使旧提取重新获得提交资格。

清空时即便尚无条目，也必须让正在生成第一条记忆的提取失效。
这里保证的是提交授权，不声称能撤回此前已发送给模型的数据。

### 2.3 实施步骤

1. 在 `MemoryService` 中引入不透明的自动提取令牌。开始提取时，在同一锁内取得授权状态、
   现有条目快照及该用户当前提取代次，避免分别读取产生不一致。
2. 模型调用放在写锁之外，隐私命令无需等待模型完成。
3. 增加自动提取专用提交入口。在现有写锁内重新检查授权和令牌，再应用提案；
   令牌失效返回稳定的 no-op，不写入，也不追加“记忆已保存”的披露。
4. 隐私操作与令牌失效使用同一把锁。对空记忆执行 clear 等无需改正文的操作，
   也必须执行失效处理；不能仅依赖文档 revision 是否增加。
5. 提取代次保存在进程内：进程重启后没有旧模型调用继续返回，因此无需新增持久字段。
   服务停止、重新装配及状态重载时也不得错误接受旧令牌。
6. 保留显式 `/remember` 的授权语义、密钥筛选、操作幂等和已公开来源条目的修改保护。
   删除仍遵守先撤回公开投影、后删除私人条目的既有顺序。
7. 检查 `/memory forget` 等相关删除入口是否存在同类迟到回写风险，复用相同失效机制，
   避免控制器重新实现另一套授权规则。

主要修改：`memory/service.py`、`memory/controller.py`，必要时在
[memory/models.py](../../src/raricy_bot/memory/models.py) 增加共享类型。

### 2.4 回归测试与验收

用 `asyncio.Event` 暂停撰写器，先完成隐私命令，再释放模型结果；不用真实网络或固定 sleep。

- 分别覆盖 off、auto off、clear，断言不发生迟到写入与成功披露。
- 覆盖 off 后重新 on、空文件 clear、用户之间互不影响。
- 覆盖正常提取、幂等重放、显式记忆命令、公开冲突和失败写入。
- 至少一项 App 集成测试使用独立的聊天与记忆 worker，复现真实装配下的并发顺序。

验收：隐私命令及时返回，旧提取失效；普通聊天仍可正常回复。

## 3. 工具能力：移除永久负缓存

### 3.1 问题与代码入口

[OpenAIModelClient](../../src/raricy_bot/core/worker.py) 将工具首轮的任何 400/404
设为 `_tools_unsupported=True`。上下文过长等普通请求错误也会触发该状态，
后续合法请求直接在本地失败。App 还依赖该共享标记转换错误类型。

相关约定：INTERFACES §14、D-19，以及
[INCIDENTS.md](../usage/INCIDENTS.md) 事件一第六节的工具能力污染记录。

### 3.2 实施步骤

1. 移除永久负缓存和依赖它的提前拒绝。单次错误不能作为端点永远不支持工具的证据。
2. 普通 400/404 仅终结当前请求，保持正常的错误分类。
3. 只有提供方返回明确、可识别的结构化“不支持工具”错误时，才对本次调用返回
   `ModelError("tools_unsupported", False)`。未知错误保留通用分类，不靠任意原始正文推断。
4. App 根据异常 kind 选择本地提示，不再读取模型客户端上的共享可变标记。
5. 用 `rg` 查所有 `tools_unsupported` 消费者、测试和其他模型调用路径，同步签名及断言。
6. 保持原来的单次调用重试规则：允许下一次用户请求访问端点，不等于自动重试本次非法请求。

主要修改：[core/worker.py](../../src/raricy_bot/core/worker.py)、
[app.py](../../src/raricy_bot/app.py) 及所有标记消费者。

取舍：真正不支持工具的端点，后续用户再次触发时仍可能收到请求；接受这一代价，
避免把一次无关错误变成持续到重启的全局故障。本轮不新增 TTL 缓存或恢复探测状态机。

### 3.3 回归测试与验收

- MockTransport 先返回 context-length 400，再返回成功；断言第二次调用确实访问端点并成功。
- 对无关 404 重复同一用例。
- 覆盖明确不支持工具的结构化错误，以及无法识别的错误。
- 覆盖共享客户端的并发请求，确认一条请求失败不改变另一条的能力。
- 保持 timeout、429、5xx 和工具后续轮错误的既有重试语义。

验收：任何请求级失败都不能永久关闭其他请求的工具能力。

## 4. 配额结算：抵抗协作式取消

### 4.1 问题与代码入口

[MessageSender.send](../../src/raricy_bot/core/sender.py) 的 `note_sent` 位于取消保护之外；
[QuotaGuard.note_sent](../../src/raricy_bot/quota.py) 只捕获 `Exception`，
无法兜住 `CancelledError`。已复现发送成功、等待记账时取消，预留持续占用额度。

相关约定：INTERFACES §10、§13、§16，D-1、D-8、D-18、D-90。

### 4.2 实施步骤

1. 明确每次 send 对预留及结算的唯一所有权，记录是否已确认送达，所有出口只能结算一次。
2. 确认送达后，将本地发送记录与配额结算收敛到一次受取消保护的终结操作。
   已确认发送必须转正，不因取消改判为未发送。
3. 保存终结任务的强引用；普通任务取消到来时，等待该操作完成后再传播取消。
   仅套 `asyncio.shield()` 不够，因为调用方仍可能提前退出，留下后台记账。
4. 覆盖等待 quota 锁、SQLite 写入和 notice 冷却持久化等取消点。
   重复取消不得导致再次 POST、双重记账或遗留预留。
5. 保持写库失败的既有降级：安全日志、可用的内存计数和预留结清；不把已成功送达改报失败。
6. 核对 App 关闭顺序，使尚在进行的结算在 Store 关闭前被等待，并遵守现有 10 秒总预算。
   不增加无限等待或没有生命周期管理的后台任务。
7. 取消发生在远端结果尚不确定时，保留既有发送/对账语义；不能为了结清预留盲目重投。

主要修改：`core/sender.py`、`quota.py` 和 `app.py` 的关闭衔接。
预计无需新增 SQL 表或持久字段。

### 4.3 回归测试与验收

- POST 已确认后取消；等待配额锁、发送记录写入、notice 冷却写入时分别取消。
- 重复取消、数据库写失败、正常失败释放、正常成功转正。
- 关闭期间等待结算，验证 Store 的关闭顺序和超时处理。
- 断言 POST 次数、结算次数、最终 pending 数、发送计数和通知冷却。
- 时间窗口测试使用可控时钟，确认预留不会跨窗口永久占额。

验收：普通协作式取消不泄漏预留，不留下无人管理的终结任务。
强制杀进程、断电或超出关闭预算时，不能承诺远端发送与本地记账跨系统原子一致。

## 5. 工作器：按可运行会话调度

### 5.1 问题与代码入口

[WorkerPool](../../src/raricy_bot/core/worker.py) 先取请求，再等待会话锁。
三个工作器遇到同一会话的三条请求时，一个处理、两个等锁，其他会话无法被领取。

相关约定：INTERFACES §12、§14、§16，D-20–D-22 的会话归属、reset 与历史提交边界。

### 5.2 实施步骤

1. 引入有界的会话调度器：每个 session 保留 FIFO 请求队列，另维护可运行 session 队列。
2. 工作器只领取可运行会话的一条请求，并将该会话标为 active。
   同会话后续请求留在队列中，不占工作器。
3. 本条结束后清除 active；若仍有积压，将会话放回可运行队列尾部，让其他会话获得执行机会。
4. 全局容量必须计算全部等待请求，包括 active 会话后面的积压。
   不得通过搬入内部无界队列制造虚假的空闲容量。
5. 统一 Router 入队、队列满判定、队列深度、readiness 和完成计数接口。
   明确等待数与执行中数量的口径，保留 join/完成跟踪能力或提供等价接口。
6. 迁移两个 WorkerPool 消费者：普通聊天和并发数为 1 的记忆命令。
   评论服务有独立调度路径，核对共享影响，不顺带替换它。
7. 保留同会话顺序、reset generation 检查、事件去重和恢复状态。
   handler 异常或取消也必须完成调度清理，关闭时不得把未处理请求误标为 done。
8. 会话无执行中请求且无积压后删除内部状态，防止字典按历史用户数无限增长。

主要修改：[core/worker.py](../../src/raricy_bot/core/worker.py)、
[core/router.py](../../src/raricy_bot/core/router.py)、[app.py](../../src/raricy_bot/app.py)，
必要时增加独立的调度模块。同步直接注入 `asyncio.Queue` 的测试和替身。

### 5.3 回归测试与验收

- 阻塞 Alice 的第一条，随后排入 Alice 两条和 Bob 一条；Alice 未释放前 Bob 必须开始。
- 同会话严格 FIFO 且绝不并发；不同会话达到配置并发数但不超过上限。
- 多个持续积压会话之间公平轮转。
- 队列满时保持既有 busy 行为，内部积压也计入容量。
- 覆盖普通异常、取消、关闭、reset、join 完成计数和空闲会话状态回收。
- 跑聊天、记忆命令和恢复相关集成测试，检查事件水位与历史提交未回归。

验收：等待会话锁不占执行容量，待处理请求总量仍受界限约束。
本次不承诺在队列已经完全占满时提供额外的按用户准入配额。
