<a id="d-1"></a>

## D-1 发送种类与两档额度

三种 kind 保持分离：reply 为模型回复，notice 为主动提示，notice_local 为明确动作的本地应答。当前默认阈值 7950/8000（D-105）：聊天以总发送数比较 reply 阈值；评论单独统计 reply，另限总量。主动提示旧的每日频道名额已由 D-18 撤销，不能让一次 help 抑制整个大厅。

<a id="d-2"></a>

## D-2 每分钟限频用滑动窗口而非令牌桶

分钟限额使用持久发送时间与在途预留的滑动窗口，避免重启清零及窗口突发。当前聊天默认 100/分钟，评论 20/分钟；旧令牌桶描述及 25 次默认值不再适用。

<a id="d-3"></a>

## D-3 busy/failure/quota 的配额归属

busy、failure、quota 都属于 notice，共用 D-18 的触发者冷却并受总额限制；不另设三套频道冷却。过载时控制提示不能突破发送预算。

<a id="d-4"></a>

## D-4 403 的三种含义如何区分与恢复

信封 403 含“跨源”或 CSRF 时视为客户端配置错误，不重试；其它权限/禁言错误使聊天不可用，定时 probe_chat 恢复。auth/me 成功不足以证明聊天权限。评论临时故障与聊天就绪隔离。

<a id="d-5"></a>

## D-5 模型输出的字符截断口径

输出按 Unicode 字符、优先自然段边界截断并留后缀空间；聊天和评论默认上限 5000。博客发布另用 UTF-16 校验且不截断（§53）。

<a id="d-6"></a>

## D-6 「私聊响应所有有效文本」里「有效」的边界

DM 同样剥去习惯性的 @机器人；无有效正文走本地提示或可读媒体路径。博客和图片扩展后的判定顺序见 D-30、D-48，不把纯媒体当普通空文本。

<a id="d-7"></a>

## D-7 直接引用不进历史；旁观消息规则已修订

直接引用只作本轮前缀，不进入历史。原“旁观消息不外送”已被 D-95 取代；大区近期公开文本可随下一次唤起外送一次，不能再宣称机器人看不到旁观消息。

<a id="d-8"></a>

## D-8 结果不确定时的对账窗口

聊天不确定发送先查 after=触发消息、limit=100；未命中最多重发一次。窗口有限，仍有重复风险，不保证 exactly-once。该策略只用于聊天；发文遵守 D-109。

<a id="d-9"></a>

## D-9 reset 的会话粒度（大区规则由 D-21 替代）

仅 DM 保留“reset 清当前会话并作废在途请求”的规则。原按作者隔离的大区方案已被 D-20/D-21 取代，大区 reset 开新公开链，不清旧链或站点消息。

<a id="d-10"></a>

## D-10 运维端点的端口与暴露

aiohttp 探针默认监听 0.0.0.0:8080，Compose 仅 expose、不发布宿主端口。响应只给固定文本与状态码，不暴露内部信息。

<a id="d-11"></a>

## D-11 重连退避的抖动幅度

先对指数退避封顶，再乘 1+U[0,0.2)；base 尊重服务端 retry。成功解析帧后重置 attempt，随机源可注入。最大配置值是抖动前的上限。

<a id="d-12"></a>

## D-12 配置项超集

配置允许在原设计上扩展，字段和校验统一放 config.py；未知普通键忽略、缺失取默认。未知 MCP feature 是 D-81 的明确例外，不能静默启用。

<a id="d-13"></a>

## D-13 「消息可能发送至第三方模型处理」的披露位置

第三方模型处理披露写进 help 和上线清单；账号资料由维护者在站点填写，机器人没有契约内的资料修改接口。

<a id="d-14"></a>

## D-14 敏感词过滤只做本地拒绝，不做内容审查

本地仅做 is_secret_probe 对系统提示、密钥与隐藏配置的固定拒绝；不额外引入内容关键词黑名单。其它回答约束交静态系统提示词。

<a id="d-15"></a>

## D-15 事件表只记录「候选消息」，不是每一条大区消息

events 只记录通过候选过滤的 DM 和精确 @ 大区消息，以 message.id 去重；无关大区流量不落表。近期消息缓冲独立且只在内存，不改变此边界。

<a id="d-16"></a>

## D-16 `last_event_id` 的两套语义：传输层「见过的最后一个」 vs 存储层「可安全提交的水位」

SSE 传输游标记见过的 message 帧，Store 水位只越过终态事件。启动和 resync 时从安全水位播种；运行期不逐帧回拨，避免重放风暴。handler 意外失败可能要等重启恢复，是已接受的限制。

<a id="d-17"></a>

## D-17 崩溃恢复用「水位补发」，而不是「启动时主动拉历史」

启动把旧非终态改为 recover，服务端按水位补发，Router 原子 reclaim_orphan；认领后再查已发回复，命中则只补终态。不另建主动拉历史的恢复通路。

<a id="d-18"></a>

## D-18 主动通知的冷却按「(频道, 触发者)」计，取消每频道 24 小时的名额

主动提示冷却按 notice:{channel_id}:{actor_id or '-'}，默认 300 秒；只有确实发送后由 quota.note_sent 写入。App 预读与 quota 使用同一键，取消每天每频道一次名额。

<a id="d-19"></a>

## D-19 模型超时不重试

本地模型超时及 HTTP 408 不重试，防止占满 worker 两个超时周期；网络错误、429、5xx 最多再试一次。SDK 重试关闭，只由模型封装统一控制。

<a id="d-20"></a>

## D-20 大区共享会话：用消息 id 映射建模，线性而非分支

公开会话键为 lobby-thread:<root_id>，归属只由回复消息 ID 映射决定；同链线性共享、不按 reply_to 分叉。映射登记不等于历史提交，重启只保留归属。活动窗口用严格大于截止时间判定；DM 不带 thread_root_id。

<a id="d-21"></a>

## D-21 大区 `/reset` 建新链，不动旧链；私聊 `/reset` 保持原样

大区 reset 以命令消息建新链，不清旧链、不作废他人请求；DM reset 清当前历史并递增 generation。公开链的所有参与者不能被一人重置。

<a id="d-22"></a>

## D-22 完整轮次提交：失败轮次不进历史（私聊一并适用）

仅在回复送达且 generation 有效后一次 append_exchange 提交完整 user/assistant 对。模型、配额、发送失败或取消不留下孤立 user，确保历史符合用户实际看到的对话。

<a id="d-23"></a>

## D-23 安全水位检查点与清理：单调、带回滚锚点、不做硬截断

持久 safe_event_watermark 单调推进，清理保留最大安全 event_id 的真实终态锚点，兼容旧版回滚。非终态不按时间删；SQLite 只设软限告警，不用硬容量限制或运行期 VACUUM。

<a id="d-24"></a>

## D-24 大区固定 system 附加说明：`texts.py` 静态常量，不插值

公开多人会话说明是 texts.py 静态常量，只拼接不格式化；用户名和消息等动态内容不得进入 system，避免把不可信数据变成指令。唯一的例外是每轮追加在 system 末尾的当前时间片段（D-114）：它由进程时钟生成、用户不可控，不构成把用户内容带进 system 的通道。

<a id="d-25"></a>

## D-25 直接引用标签：大区 `[直接引用 @作者]`，私聊维持 `[引用 @作者]`

大区直接引用标签为“直接引用 @作者”，DM 保持“引用 @作者”；两者都在 user 内容中，不能为统一措辞改变已有私聊语义。

<a id="d-26"></a>

## D-26 评论发现与聊天生命周期隔离

评论以最近列表和通知两个轮询器发现，共享原子 claim 与模型 gate，独立队列/配额/上下文。读写临时失败不影响聊天 readyz；关键后台任务退出影响 livez。标已读失败只重试标记，不重新回复。

<a id="d-27"></a>

## D-27 评论冷启动尾页、超限终态与 Service quota 生命周期

冷启动最多五页仍有尾页时保存 cutoff，不能写 baseline_done；超大完整树按稳定终态跳过或通知 unmatched，不能用前缀匹配。reset 意图在 claim 前确定；模型前预留评论 quota，所有出口结清，恢复异常走 recover+退避。

<a id="d-28"></a>

## D-28 图片只进当前轮，历史里记标记

图片字节只进当前轮，历史留下图片或未提供标记。避免后续每轮重复发送大体积附件，且让缺失图片的提问仍有可解释的上下文。

<a id="d-29"></a>

## D-29 图片由我们自己取回并转成 data URL，不把站点 URL 交给模型商

宿主同源下载并编码 data URL，不让模型商回源读取站点 URL。请求前核对 scheme/host/有效端口、限制字节数；按字节识别 PNG/JPEG/GIF/WEBP，拒绝 SVG，不信任 DTO MIME。

<a id="d-30"></a>

## D-30 取图失败降级为纯文本轮；纯图失败转本地提示且用 `notice_local`

取图失败且有正文时纯文本回答并留缺图标记；纯图失败回 notice_local，不占主动提示冷却。模型不支持视觉导致 400 时不偷偷重试纯文本，以免隐藏部署错误。

<a id="d-31"></a>

## D-31 `/search` 是单轮能力授权，而不是全局联网开关

search 等能力由显式命令授权当前一轮；后续普通聊天和评论不继承工具权限。命令前缀剥离后仍经过本地命令与输入规则。

<a id="d-32"></a>

## D-32 MCP 工具发现与产品能力绑定分离

Provider 发现工具不等于允许执行；只有 feature 绑定可生成 server__tool 定义，执行前再次校验。Exa 仅允许已有白名单工具，不能依模型自觉避免网页抓取等额外能力。

<a id="d-33"></a>

## D-33 Exa 参数、结果和隐私边界由宿主强制

宿主钉死 Exa 参数、结果数、URL 校验和当前/历史摘要预算；查询、URL、摘要、工具参数和原始响应不落日志/SQLite。原“stderr 全部丢弃”已由 D-91 的受控诊断替代，D-91 的“记录原文”部分又由 D-111 取代（现在只提取失败类别与模块名）。

<a id="d-34"></a>

## D-34 MCP 是软故障扩展，不参与健康判定

MCP 连接、凭据、工具发现或模型 tools 不支持只停对应能力；普通聊天、评论与健康端点不受影响。确定缺环境不重连。原「确定模型不支持 tools 时在本进程缓存」已由 D-116 取代：该结论只属本次调用，不写共享状态。

<a id="d-35"></a>

## D-35 搜索上下文只在送达后提交

工具消息仅属当前两轮请求；送达后才保存问题、压缩摘要和回答。取消、失败、配额拒绝或 reset 竞态不得提交原始 MCP 内容或孤立工具消息。

<a id="d-36"></a>

## D-36 Exa 多 Key 是一个逻辑 Provider，轮询与故障转移都有界

多个已授权 Exa Key 包成一个逻辑 Provider，模型仍见一个工具。按 ready 槽位轮询，同次逻辑调用每槽最多一次，成功立即停止；不复制 feature 以暴露池结构。

<a id="d-37"></a>

## D-37 槽位状态只存内存，重启后重新探测

槽位 ready/cooldown/exhausted/invalid/disabled 只在内存；重启重新探测，避免把外部充值等变化误当永久失效。不持久化 Key 或稳定指纹。

<a id="d-38"></a>

## D-38 `/kb` 这一轮把 `context_input_tokens` 当硬上限（P0-05）

KB 资料轮允许将历史整对丢光（feature_context），普通聊天仍保留最后一对。此参数不截断 system/当前输入；调用者须先做预算预检，不能把它当成任意输入的硬截断器。

<a id="d-39"></a>

## D-39 能力命令最多一个：能力冲突先于其它本地判定

最多解析一个能力命令；剥离后又遇能力前缀则本地拒绝，避免同条消息叠加资料外送授权。help/reset 属本地动作，不算第二种能力。

<a id="d-40"></a>

## D-40 内池故障转移不增加模型工具调用，但可能消耗多个上游请求

池内故障转移仍是一笔模型工具调用，但可能多次请求上游，超时后也可能重复计费。每槽至多一次且成功即止；运维估算不能只看模型调用数。

<a id="d-41"></a>

## D-41 知识库是本地只读能力，不是 MCP 工具

KB 是本地只读检索，走普通 complete，不依赖 MCP、Exa、模型 tools 或 CapabilityLimiter；授权标记在请求层交汇，检索实现保持分层。

<a id="d-42"></a>

## D-42 一级目录即分类，根目录文件归 `_root`

KB 一级目录作分类，根文件归 _root；分类和相对路径会展示给用户及模型，目录命名也必须经过可见范围核对。

<a id="d-43"></a>

## D-43 KB 命中原文只进当前轮的 user 消息，历史不保存原文

KB 原文只进本轮 user，历史仅保留去掉块的问题与回答；静态 KB_SYSTEM_ADDENDUM 不插值。一次检索授权不能变成持续外送原文。

<a id="d-44"></a>

## D-44 KB 默认只允许私聊 + 用户 ID allowlist

KB 默认关闭，DM+稳定用户 ID allowlist；开放大区须显式配置 all_chat，且仍须精确 @。拒绝时不透露目录、分类或是否命中。

<a id="d-45"></a>

## D-45 Exa 池与 KB 都是软故障扩展，不参与健康判定

Exa 池全不可用或 KB 刷新失败只降级显式能力；KB 可保留最后有效快照，健康端点不因索引刷新而抖动。

<a id="d-46"></a>

## D-46 无法可靠分类的上游错误一律安全失败（P0-02 的处置）

仅对已验证的结构化字段和固定错误标记分类；未知错误为 unknown_upstream，不轮换、不冷却，最终稳定失败。不能凭猜测把健康 Key 判成额度耗尽。

<a id="d-47"></a>

## D-47 聊天区引用的博客：正文进模型，但只属于当前轮

用户主动引用博客时取回可用正文，只属当前轮；历史留状态标记，聊天长度键独立于评论。带块时允许清空历史。原匿名取回策略已由 D-104 改为携带 Cookie。

<a id="d-48"></a>

## D-48 空正文的判定顺序：博客先于图片；被引用消息的三种边角也留痕

空正文先判断博客再判断图片，避免视觉关闭吞掉可读博客。引用删除、纯图、无正文各留标记；删除优先于内容。原“缩略图不下载”已由 D-54 撤销。

<a id="d-49"></a>

## D-49 引用语法在三条通路上都展开，但历史里只留用户自己写的那十个字

内容引用在聊天正文、引用博客、评论路径共用解析器；实际展开仅属当前轮，历史保留用户原始 [@id]。各路径沿用自身预算，原文超限不先抓取再丢弃。

<a id="d-50"></a>

## D-50 引用解析用上游源码里的两个 GET，本地契约同步到上游新版

剪贴板与投票 GET 的补充依据是上游源码，不因引用渲染文档存在就假定端点已被完整约定。固定按 ID 走带登录的信封接口、受响应上限约束；401 不额外重登录。材料当前同步版本见文档索引。

<a id="d-51"></a>

## D-51 预算先算再取回；取回处数与图片张数各有独立上限

先决定预算再取回，塞不下既不请求也不替换；每次 resolve 最多取 10 处、图片另限 3 张，同 ID 本次缓存、不跨轮。视觉关闭不取字节；失败占位有界，不靠“只认第一条”替代字符预算。

<a id="d-52"></a>

## D-52 投票也解析成文字块，尽管站方在聊天与评论里刻意不展开

9 位投票取回并转换为不可信文字块，即使站点聊天 UI 不展开投票。模型需要内容而非可点击组件；标题和选项单行清洗，失败有明确标记。

<a id="d-53"></a>

## D-53 评论区的图按「名额」分配，而不是各段各自封顶

评论共享图片尝试名额，按附件→评论引用→文章引用分配，失败同样扣减；默认 3，0 可只关闭评论视觉。纯图直回失败使用 notice_local；忙碌/失败/额度提示仍静默。不解析文章手写 img。

<a id="d-54"></a>

## D-54 被引用消息的缩略图也取回来交给模型（撤销 D-48 的最后一段）

SQLite 连接由实际工作线程持 threading.Lock；open/close 状态另用 asyncio.Lock。to_thread 的 await 取消不会停线程，协程锁提前释放会使另一线程同时访问连接。

<a id="d-91"></a>

## D-91 子进程 stderr 进日志：有界、压成单行、且必须在脱敏之后（**已由 D-111 取代**，仅存档）

MCP stderr 仅收末尾 2000 字符，启动/重连失败时压单行并脱敏后记录；读线程持有并关闭读端，避免管道阻塞与 fd 复用。凭据同时登记出站和日志 Redactor，替代 D-33 的全部丢弃。

D-111 取消了「stderr 原文进日志」这一条：精确字符串替换不承诺识别 URL 编码、JSON 转义或跨截断边界拆开的秘密，因此不能把「已过脱敏」当作可以保存任意正文的依据。有界缓冲、持续排空管道、读线程持有并关闭读端这三条仍然有效，并且是新的结构化提取器的基础。

构建与部署统一使用 mcp-tools.package.json 的版本和 overrides，不逐个 npm install。原 SDK 提升冲突可让 Wolfram 缺少 server/mcp.js；安装顺序不能作为依赖保证。

<a id="d-98"></a>

## D-98 普通用户名、博客正文与已展开的公开剪贴板都能触发

本地公开索引中的完整、区分大小写 username token 可触发，@ 仅影响优先级。来源限本轮允许的作者/引用/会话/博客/已展开文本/近期块；不扫描模型回答、搜索、MCP 或 KB，不模糊匹配，不额外抓被省略正文。

<a id="d-99"></a>

## D-99 文本命中一律经站点精确校验，任何不确定都 fail-closed

纯文本命中须查询站点并唯一精确同名、owner key 一致；稳定 subject 无需重复查询。任何歧义或失败不用候选。正/负缓存 600/60 秒、512 项、15 次/分钟，仅缓存身份结果，不记查询/身份日志。

<a id="d-100"></a>

## D-100 两阶段删除的崩溃语义：先撤回、再删除

forget/clear 先 cmd:<message_id>:unpublish 撤回，再 cmd:<message_id> 删除私有；撤回失败停止。崩溃可幂等续行，最坏保留私人来源而非遗留公开副本；空公开文件保留 operations。

<a id="d-101"></a>

## D-101 `public_conflict`：已公开来源不得被 AI 或自动记忆静默更新

STATUS_PUBLIC_CONFLICT 是第十一个稳定状态：更新仍公开的私人来源，或同 key add 替换，都拒绝且不写两边；公开状态不明则 unavailable。自动提取静默跳过，显式 remember 给专用文案；用户先撤回再修改重发。

<a id="d-102"></a>

## D-102 `/memory off` 不撤回公开条目

memory off 只暂停私有读取和自动提取，不撤回公开条目；reset 不动长期记忆。撤回由显式 unpublic/forget/clear 发起，不让读取开关产生隐藏的对外后果。

<a id="d-103"></a>

## D-103 公开个人记忆的跨模块补充约束

公开扩展的字段与签名见现行代码和 §39–§52，保留以下跨模块约束：

实施期逐项字段裁决与 R 编号原表保留在归档，不再维护重复的类型定义。

## D-108 跨日计费用闭区间 `[budget_from_day, charged_through_day]`，不把对账时刻冒充发布时间

预算按 UTC+8：published 按预留日 budget_from_day 至本地确认日 charged_through_day 的闭区间每日占 1，inflight/unconfirmed 跨日持续占 1。confirmed_at 不是发布时间；明确 429 才清本次区间，重试重新计费。额度满不挡只读对账，宁可保守多占。

## D-109 结果不确定时只对账、不自动重投：接受漏发与人工核实，不用重复发布换成功率

网络/超时/5xx/非法信封/成功缺 ID/取消均不确定，保留占额、只对账、不重投。仅合法业务拒绝信封释放额度；仅稿库明确 429 可同指纹累计少于 3 次时重试。对账需唯一精确凭证，空或不完整查询不是失败证明；12 次未确认后停查询仍占额。启动 inflight→unconfirmed、queued/running→interrupted，不重新生成。

## D-111 日志字段名白名单之外再加取值类型；MCP 用结构化分类取代原始正文与 stderr 尾部

`LOG_FIELDS` 由 `FIELD_KINDS` 派生：每个字段同时登记**取值类型**，不满足就整条丢弃，不截断也不转写。只挡字段名挡不住 `error=describe_error(exc)` 这种把上游正文塞进合法字段名的写法。`error` 因此只接受 Python 类名，`module` 只接受经校验的 npm 包路径，`stack` 只接受 `模块.函数:行号` 列表。

`describe_error` 从返回自由文本改为返回受限字段（异常类型、数字错误码、退出码，`BaseExceptionGroup` 只展开有界深度）；MCP stderr 改为按固定规则提取失败类别与模块名，原文一概不留（取代 D-91）。理由：正文来自上游，可能含密钥或用户内容，而精确字符串替换不承诺识别任意编码与截断边界；诊断真正需要的分类信息本来就不在正文里。stdio 的增量 UTF-8 解码与持续排空管道保留。

控制台脱敏作用在 handler 的**最终输出**上（`RedactingFormatter`），覆盖消息、extra、`exc_text` 与 `stack_info`，不再改写共享 `LogRecord`：后者会让多个 handler 的先后顺序决定安全性。归档的 JSON 编码顺序另见 D-112。第三方 WARNING 及以上在控制台与归档都换成 `third_party.failure`，低于 WARNING 的第三方行保持原样。

## D-112 永久错误归档是与控制台平行的独立通路：分片只增不删，且只收已清洗事件

新增 `error_archive.py`：单写者 JSONL，按 UTC 日期与大小分片，`os.O_EXCL` 独占创建，文件名含 `boot_id` 与递增序号；不使用会按 `backupCount` 淘汰旧文件的轮转策略，也不提供 `retention_days` / `max_files`。归档门槛独立于控制台级别（控制台设成 ERROR 时 WARNING 仍须归档），INFO 只收白名单事件。每条写入后 flush，ERROR/CRITICAL 额外 fsync，其余按 `fsync_interval_seconds` 批量同步。

四条约定的理由：**重启不会往旧分片追加**，所以旧分片只可能被磁盘损坏，写入端的重启恢复退化成一次只读巡检；**归档自己的状态事件只走 stderr**，否则一条写失败会变成递归；**写失败隔离后继续服务**并累计缺口计数，未落盘的事件不假装可以补回；**损坏分片保留原样**，读工具跳过末行而不修复，否则「写到一半就断电」的文件会显得完全正常。

归档已启用却打不开目录时退出码 3，不假装永久记录已生效。运行中磁盘满/权限变化/I/O 错误只隔离归档，不影响 `/livez` 与 `/readyz`（否则宿主会重启一个仍在正常收发消息的进程），改由独立的 `/archivez` 暴露计数。归档目录须与知识库、记忆、稿库和数据库目录互不重叠 —— 但**只在启用时检查**：关闭时它没有任何风险，却会让 `storage.db_path: ./bot.db` 这类旧配置因为一个从不写盘的目录而起不来。

另有四条必须在实现里保持的性质（2026-09-21 只读审查后补齐，每一条都有对应回归测试）：

- **归档同样脱敏，但先处理值再编码 JSON**。`_serialize` 使用与控制台同一凭据表，递归替换字符串值后才编码；字段名和数值元数据保持结构语义。此规则替代先编码再替换：引号、反斜杠经 JSON 转义后会让原密钥匹配失败，数字密钥还可能破坏 JSON 数字。字段类型约束只保证形状，不能代替内容脱敏。
- **状态事件在锁外发出**。`logging.Handler.handle()` 先拿 handler 锁再调 `emit()`，而 `emit()` 要拿归档锁；若 `disk_low` / `write_failed` 这类事件在持锁时发日志，两条真实路径就构成 ABBA 死锁，后果是机器人整体卡死。实现用 outbox：锁内只记"待发"，出了锁再发。
- **换片/写入失败可重试**。旧文件已关、新文件没建起来时必须允许下一次写入重试打开，并逐条累计缺口；否则归档会悄悄停止工作，而 `/archivez` 之外没有任何迹象。部分写入、短写或 flush 失败可能留下不完整 JSON 行，后续记录必须改写新分片，不能沿用旧句柄再宣称恢复；旧分片不删除、不截断、不重写。恢复事件同样不能绕过这条边界。
- **跨 UTC 日期换片**。只按大小换片时，低流量日的分片会带着旧日期继续接收新条目 —— 而运维手册告诉备份方"文件名里是旧日期的都已关闭"，那些分片的后半段就永远不会被备份。

## D-113 `allow_plain_http` 只对回环地址例外，公网明文没有任何配置能放行

`site` 与 `model` 的 `base_url` 对非回环地址**无条件**要求 https，并拒绝 URL 中的 userinfo、查询串与片段。回环地址的 http 也需要显式打开 `allow_plain_http`（默认关闭）。

理由：站点带会话 Cookie、模型带 API Key，明文 HTTP 会把两者连同正文一起交给链路上的任何人。这不是一个"我确实知道自己在做什么"能解锁的选项，所以开关不提供全局覆盖 —— 它只用来省掉本机开发时反复写 https 的麻烦。userinfo 与 query/fragment 单独拒绝，是因为它们能把凭据或任意文本带进异常文案与请求目标，而脱敏登记的只是"配置里那个 Key"。

## D-114 系统提示词里的当前时间片段是唯一允许的动态内容

`time_context.render_current_time` / `append_current_time` 把一行 `当前时间：YYYY-MM-DD HH:MM 周X`（UTC+8，到分为止，定长 24 字符）追加为 system 的**最后一段**，排在 `system_prompt`、全部静态附加说明与两条记忆说明之后（`INTERFACES.md` §54）。聊天与评论经由 `ContextManager` 组装，两处预算路径共用私有方法 `_time_fragment`；评论无 `context_manager` 的回退分支与 `blog/writer.py` 各自调用 `append_current_time`。三处同源，不存在第二份渲染实现；记忆撰写器不追加该片段。

这是 D-24 与 `SYSTEM_PROMPTS.md` §1.6「system 附加说明必须静态、不含占位符」的**唯一**例外。它安全，是因为那条红线的目的只是「用户可控的内容不得进 system」（`INTERFACES.md` §19 第 2 条）：片段由 `now()` 从进程时钟生成，用户完全不可控，不构成那条通道；反过来放进 `role="user"` 会被模型当成用户说的话，并随 `append_exchange` 进历史、每轮堆一个时间戳。

三条防止例外被放宽的边界：

- 片段只由 `now()` 渲染，**不接受任何额外入参**，结构上没有位置装进请求、用户、记忆或工具数据。
- 它**固定是 system 的最后一段**，排在 `system_prompt`、所有静态附加说明与记忆说明之后，不得排在其它 system 内容之前。
- 此后任何新增的动态 system 内容都必须**重新走一次决策记录**，不得援引本次例外。

## D-115 自动提取的提交授权在写锁内原子复核（令牌 + 进程内代次）

`MemoryService.begin_auto_capture` 在**同一把写锁**内一并取得用户的授权状态、条目快照与该用户的
提取代次，返回不透明 `AutoCaptureToken`（`memory/models.py`）；模型调用放在锁**之外**，隐私命令
因此无需等待模型返回。`commit_auto_capture` 在写锁内复核 token 的 epoch、`_enabled`、
`document.auto_capture` 与该用户 generation，任一失效即返回稳定 `noop`（不写入、不追加
「记忆已保存」披露）。失效入口是四个隐私 mutation：`set_auto_capture(False)`、
`set_private_enabled(False)`、`clear_private`、`delete_private`；失效处理放在幂等命中之后、
应用之前，因此**值未变的 no-op 路径**（空记忆 clear、`auto_capture` 本来为 False）同样失效，
不依赖文档 revision 是否增加。代次与纪元都是**进程内**字段（`_capture_generation` /
`_capture_epoch`），不落盘、不迁移表；`stop()` 递增纪元，使停止前发出的令牌全部失效。

理由：聊天与记忆命令走两个独立 `WorkerPool`，会话锁不共享；`MemoryService` 的写锁只保护单次
mutation，挡不住「等待模型期间完成的隐私操作被迟到结果越过」。授权规则的唯一实现留在服务层，
控制器不再自建一套（旧路径在撰写前查开关，无法阻止提交）。这条保证的是**提交授权**，不声称能
撤回此前已经发送给模型的数据。

## D-116 端点「不支持 tools」只属本次调用（取代 D-34 的进程内缓存）

`OpenAIModelClient` 不再持有「tools 不支持」的共享可变标记：普通 400/404 只终结当前请求并归类
`bad_request`。`tools_unsupported` 只在提供方给出**结构化**错误时产生
（`core/worker.py::_is_tools_unsupported`：`error.param` 精确为 `tools` / `tool_choice` /
`parallel_tool_calls`，且 `code` / `type` 命中窄白名单），且只是**本次调用**的结论。App 与

—— 漏判只让一次调用按普通错误处理，误判却会把无关错误改写成「能力不可用」，二者不对称。
本轮不新增 TTL 缓存或恢复探测状态机。

## D-117 配额结算抗协作式取消：所有权模型 + 受取消保护的终结

`MessageSender` 引入 `_Delivery(result, record, charge)` 所有权模型：`_deliver` / `_on_error` /
`_reconcile` 只做 POST 与对账、**不结算**；`send` 是唯一结算点，确认送达后由 `_commit_delivery`
把 `store.record_sent` 与 `quota.note_sent` 收敛成一次受取消保护的终结操作（`_run_settlement`：
`ensure_future` + `shield` + 强引用集合 `_settle_tasks`）。重复取消只提前传播，内层 task 不在
取消作用域内，因此不二次 POST、不双重记账。新增公开方法 `MessageSender.wait_settled()`
（跨模块契约见 §13），`app._shutdown` 在 `Store` 关闭前调用它（§16）。`QuotaGuard.note_sent`
用 `settled` 标志 + `except asyncio.CancelledError` 兜住结算中途的取消（§10）。

已知边界：强制杀进程 / 断电 / 超出既有 10 秒关闭预算，不承诺「远端发送」与「本地记账」跨系统
原子一致；事件循环整体拆除时仍存活的终结 task 被 cancel，该硬路径下内存预留可能丢失。远端结果
尚不确定时被取消仍按既有语义释放预留、不盲目重投（D-8）。

## D-118 工作器按可运行会话调度（`core/scheduler.py::SessionScheduler`）

每个会话一条 FIFO 等待队列，另维护一条可运行会话队列；工作器只领取**可运行会话**的一条请求并
把该会话标 active，同会话后续请求留在队列里、不占执行容量。本条结束清除 active，有积压则把会话
放回可运行队列**队尾**（公平轮转，不饿死）。这取代旧顺序「先从全局队列取一条、再等会话锁」——
后者在三个 worker 遇到同一会话三条请求时，一个处理、两个等锁，把别的会话挡在全局队列里。

容量口径：`qsize()` / `full()` / `empty()` 是**未派发的等待请求数**（含 active 会话后面的积压，
与 `asyncio.Queue`「get 后即出队」一致），`active_count` 是执行中请求数（≤ 并发数）；任何时刻
等待数不超过 `maxsize`，没有搬进无界内部队列制造虚假容量。`put_nowait` 仍抛
`asyncio.QueueFull`，Router 的 busy 语义不变；`MessageRouter` 的队列参数类型改为
`EnqueueQueue`（§12）。空闲会话状态（无执行中且无积压）被回收。

与 D-20–D-22 的关系：会话归属、大区 reset 建新链与完整轮次提交的边界不变；本项只改「取请求
与排队的顺序」，同会话串行、generation 检查、事件去重与恢复状态照旧。关闭语义：worker 被取消时
不会把**未领取**的请求误标 done（它们留在等待队列里），因此 `stop()` 之后 `join()` 会因未处理
积压而挂住 —— 这是刻意的，且没有任何调用方在关闭时 `join()`。评论子系统仍走自己的调度路径。
