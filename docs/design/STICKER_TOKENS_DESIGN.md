# 表情包出站规范化设计

聊天与评论回复里的表情包（站点语法 `[@合集/表情]`）目前完全依赖系统提示词里的名字表。
模型会写错名字或格式，而站方契约规定**写错的名字不报错、不破图，只是原样显示给读者**，
因此这类错误纯靠提示词兜不住。本设计把「格式与正确性的所有权」从模型移到代码：
模型只提供查找线索，出站字节一律由代码生成。

实施完成后本文件按 [文档索引](../README.md) 的维护规则移入 `archive/`，
现行规则同步进 `INTERFACES.md`（新增 §55）与 `DESIGN_DECISIONS.md`（新增 D-119）。

## 1. 背景与问题

线上观察到两类失败：**名字写错或编造**、**格式写错**（不是「该发而不发」）。
`src/raricy_bot/` 内没有任何表情包相关代码，出站链路上也没有形态校验，
模型写什么就发什么。

## 2. 目标与非目标

**目标**

1. 读者永远看不到因我方生成的非法表情 token 而残留的字面量（边界见 §6）。
2. 提示词里的名字表只有一个真值源，不再出现两处清单。
3. 出站长度预算仍然只有一个最终权威，不被新增长顶穿。
4. 聊天与评论两条链路行为一致，包括各自的短期历史。

**非目标**

- 不访问 `GET /api/stickers`，不做清单动态刷新（真值源锁定在部署配置）。
- 不引入工具调用，不给聊天主路径加 tools 参数。
- 不做模糊纠正（编辑距离、子串匹配）。
- 不把本功能扩展成任意合集支持。
- 不改评论的配额、去重、事件状态机。

## 3. 已核实的契约事实

均来自站方契约 [chat-bot.md](../materials/chat-bot.md)，实施时以该文件为准。

| 事实 | 位置 |
|---|---|
| 表情是**正文文本** `[@合集/表情]`，渲染期展开，两端都是名字而非 ID | §7.4 |
| **名字写错 = 读者看见原文**；不报错、不破图、不产生通知 | §7.4 |
| 一条消息最多 30 个，超出部分原样显示 | §7.4 |
| 两段各 ≤32 字符，无空白，字符集为 Unicode 字母 / 数字 / `+` `·` `-` | §7.4 |
| 清单里可能列出含 `_` 等集合外字符的名字，**列得出来但 token 永远匹配不上** | §7.4 |
| 站长随时可能删素材或把合集标 `ignore`，清单不是永久配置；token 失效只显示原文 | §7.4 |
| 表情只在讨论与评论里生效 | §7.4 |
| 内容引用 `[@a1b2c3d4]` / `[@AbCdEf1234]` / `[@vOtE12345]` / `[@123456]` **没有斜杠** | §7.3 |

## 4. 设计总览

新增两个模块、改四个接线点。

### 4.1 出站管线：`outbound.py`（新增）

单一函数负责最终预算，聊天与评论共用：

```python
def prepare_outbound(text, *, redactor, table, max_chars) -> tuple[str, OutboundReport]
```

步骤与顺序（每步的输入输出都是明确的，后两步只依据第 2 步产出的区间表，不回头猜）：

1. `redact` —— 脱敏是本项目的隐私边界，最先执行。
2. `render` —— 表情归一（§4.2）。**可能增长**，所以必须排在截断之前。除正文外还返回
   **归一后正文的区间表**：每个表情 token 的 `(start, end)`，以及每个代码区的 `(start, end)`。
3. **逐 token 敏感串复检** —— 归一可能重新拼出已登记的敏感字符串，见下。
4. `truncate` —— 按「长度预算」的口径截断。
5. **区间回退** —— 切点落在 token 或代码区内部时回退，见下。

**逐 token 敏感串复检（必须，不能只写进测试）**

`redact → render` 这个顺序本身有洞，且只靠 App 兜不住（评论路径没有 App 的提前 render）：

- 脱敏器是按登记字面量做 `str.replace`（[redact.py](../../src/raricy_bot/redact.py)），
  所以 `[@14/上 班]` 里的空格让敏感串「上班」匹配不上；
- 随后 render 的去空格容错正好把它拼回完整敏感串，**归一反而生成了第 1 步没能拦住的字符串**。

做法：对每个**归一后**的 token 再跑一遍脱敏器，命中则**整枚丢弃**。不能替换成
`[redacted]`——那会在正文里留下一个非法 token，正是本设计要治的病。
这一步是完备的：render 唯一会新建的文本就在 token 内部，token 之外的正文已在第 1 步脱敏过。

**长度预算（`max_chars` 的语义 = 含截断提示的最终上限）**

`truncate_at_paragraph` 在发生截断时返回 `text[:cut].rstrip() + TRUNCATION_SUFFIX`
（`TRUNCATION_SUFFIX` 是 `"\n\n（内容过长，已截断）"`，12 字符），因此它最多返回
`limit + 12` 字符。实测 `limit=5000`、输入 5001 字符 → 输出 **5012 字符**；
而 `behavior.max_output_chars` 默认 5000 恰好等于站方 §7.1 的正文上限，
这样一个长度会被站点以 `tooLong` 直接拒绝、整条发不出去。这个既有越界由本设计的口径一并收口：

- 未超出 `max_chars` 时不截断、不追加提示，原样返回。
- 需要截断时只传 `limit = max_chars - len(TRUNCATION_SUFFIX)`，输出上界于是回到 `max_chars`。
  越界**不在 `truncate_at_paragraph` 内部修**：它的契约本来就是「`limit` 不含提示」
  （`tests/test_text_utils.py` 钉住 `limit=10` → `"abcdefghij" + SUFFIX`，共 22 字符），
  改它会推翻既有语义。收口只能由调用方在 `prepare_outbound` 里传扣减后的 `limit` 完成。
- 极小预算：`max_chars <= len(TRUNCATION_SUFFIX)` 时放弃提示、直接硬切 `text[:max_chars]`；
  `max_chars < 1` 时返回空串。提示本身不允许把正文顶出上限。

**切点与区间回退**

`truncate_at_paragraph` 不返回切点，而**从结果字符串反推切点既脆弱又会混淆「提示之前」与
「字符串末尾」**：硬切后残片可能长这样，残片并不在末尾，且与末尾隔着一整个段落——

```text
正文[@14/

（内容过长，已截断）
```

因此 [text_utils.py](../../src/raricy_bot/text_utils.py) 新增
`truncate_with_cut(text, limit) -> (body, cut, truncated)`，由现有 `truncate_at_paragraph`
委托给它，既有调用点签名全部不变。

拿到真实切点后，在**追加提示之前**判定并回退：

- 切点落在某个表情 token 区间内部 → 回退到该 token 起点。
- 切点落在某个代码区区间内部 → 回退到该代码区起点。否则关闭反引号被切掉后，
  原本受代码区保护的非法 token 会暴露为普通正文；若那个名字恰好合法，
  它还会反过来**渲染成表情**，与模型「展示这个语法」的意图正相反。

回退只减不增，且只作用于区间表里已记录的区间，不按正则猜归属，因此不会误伤
无斜杠的内容引用 `[@a1b2c3d4]`。

**幂等不变量（承重）**：`render` 对已规范化的 token 是恒等变换。因此
[app.py](../../src/raricy_bot/app.py) 的披露路径可以预先把回答 render 一遍、按既有算法算预算，
Sender 再跑一遍时不会增长，那套三段预留（披露 + 脱敏增长 + `TRUNCATION_SUFFIX`）依然成立。
这条必须有专门测试。

### 4.2 扫描与判定：`stickers.py`（新增）

纯函数，无 IO、无网络、不依赖 `SiteClient` / `Store`，因此可单测、可同时被两个 Sender 使用。

```python
@dataclass(frozen=True)
class StickerTable:
    collection: str
    names: tuple[str, ...]                 # 有序规范名，供提示词生成
    _lookup: Mapping[str, str]             # MappingProxyType；frozen=True 不冻结字典

    @classmethod
    def from_config(cls, cfg) -> StickerTable: ...
    def resolve(self, clue: str) -> str | None: ...

def render(text: str, table: StickerTable) -> RenderedText: ...
# RenderedText: .text 归一后正文 / .token_spans 表情区间 / .code_spans 代码区区间 / .report 计数
```

判定规则：

- **判别式是斜杠**。候选必须有 `合集/名称` 结构；`[@a1b2c3d4]` 这类无斜杠的内容引用
  一律不进入本流程。
- **只归一候选内部**（宽度、候选内空格），**不对整条正文做 NFKC**。
- **未闭合候选不跨段落寻找结束位置**，避免吞掉后续正文。
- 命中后由代码重写为 `[@collection/规范名]`：模型看到的格式与最终字节由代码决定。
- 未命中且**已可靠判定属于表情语法**的候选整段剥除。
- 单条消息超过 30 个时只保留前 30 个，其余剥除。
- **不做模糊纠正**。唯一候选不等于唯一意图（「上学」可能被纠正成「上班」，
  「不要」可能被子串命中「不」），格式正确了表达却变了。首版只启用宽度归一、
  空格容错、精确匹配与配置别名。

**代码区扫描**（不复用 `content_refs.py` 的简化扫描器，它不适合作为可靠实现）：

- 围栏：```` ``` ```` 或 `~~~`，≥3 个字符，闭合围栏须同字符且不短于开启；
  **未闭合围栏按 CommonMark 延伸到文本末尾**。
- 行内：反引号 run 必须**等长 run** 配对；**未配对的单个反引号是普通文本**。
  这条不能写反——把未配对反引号当作代码区起点，会让其后整段正文被误判成代码区，
  那正是本设计要治的漏字面量。
- **歧义时偏向「不是代码」**：两种误判都有代价，但代价不对等。
  误判成代码会漏出字面量，那是读者可见的缺陷；误判成非代码会改动本应逐字保留的代码区文本，
  与下一条「代码区不动」相冲突，属于**已知的取舍代价**，而不是「无害」。
- **代码区内的候选一律不动**，保留原文。模型既然把它放进代码块，意图就是展示这个语法
  （契约里代码块内的 `[@id]` 本就不展开），剥除或重写反而破坏了它的表达。
  代价是模型若在代码块里写了错名字，读者会看到那段字面量——但那是它自己选择展示的文本，
  不是漏出去的 token。**截断不得破坏这个保护**，见 §4.1 的区间回退。

### 4.3 配置与加载期校验

`config.yaml` 新增小节，`config.example.yaml` 同步（带中文注释）：

```yaml
stickers:  # 表情包出站规范化；关闭时完全不介入正文与提示词
  enabled: false   # 总开关；代码默认关闭，与其它可选子系统一致
  collection: "14"  # 站点素材目录名；当前只支持 14，其它取值启动失败
  entries:          # 名称必须与站点素材完全一致
    - name: 上班
      aliases: []   # 可选；模型可能写出的同义说法，用于精确匹配的第二张表
    - name: 不
```

45 个名称的完整列表是**部署配置的事**，不放本文件、也不放 `texts.py`（见
[文档索引](../README.md) 的维护规则：每类事实只维护一个主要来源）。

加载期校验（`config.py`，沿用既有 `ConfigError` 风格，错误不回显取值）：

- `collection` 必须是 `"14"`；两段都必须过长度与字符集检查，而是**两段**。
- 名称非空、≤32 字符、无空白、字符集 ⊆ Unicode 字母 / 数字 / `+·-`。
  **这一步把契约里那个坑挡在启动时**（名字含 `_` 会在线上静默变成字面量），
  而不是留到运行期。
- 无重名；名称与别名之间、别名与别名之间都不得相撞。
- **碰撞必须在同一归一规则之后检查**，否则全角 / 半角会生成相同的 lookup key。

迁移注意：本仓库检出的 `config.yaml` 里并没有那段【关于表情包】文字
（`system_prompt` 只有三行），因此那段提示词在**实际部署的配置**里。
迁移时按部署配置删段、把名称搬进 `stickers.entries`。

### 4.4 提示词

`system_prompt` 里手写的【关于表情包】整段删除，改由代码从配置生成，挂到现有
`system_addendum` 通道。模板与构造函数放 `texts.py`（与
`texts.memory_auto_capture_text` 同类的文本构造函数，不是模块级常量）：

```python
def sticker_system_addendum(*, collection: str, names: Sequence[str]) -> str: ...
```

正文口径（回应两处原有矛盾）：模型**看得到**格式，但最终合集与名称由代码决定；
不再声称「写错的名字会被读者看到原文」——本地会剥除，但配置合法而素材已下线的
token 仍会显示原文，那不是我们承诺能拦住的。

> 需要时使用 `[@14/名称]`，名称只从下表选择。不确定时不发送，不编造名称。
> 不要为了发送表情而把它放进代码块。

最后一句是**故意给模型一个安全的失败方式**：把它的犯错模式从「编造」推向「不发」，
而「不发」由代码兜着，没有代价。清单按名称平铺。

**这是一条新的静态附加说明来源**，必须遵守既有约束并新记一条决策：

- [SYSTEM_PROMPTS.md](SYSTEM_PROMPTS.md) 规定 system 附加内容必须静态、不含占位符、
  不含用户可控内容；D-114 明确「此后任何新增的动态 system 内容都必须重新走一遍决策记录，
  不得援引本次例外」。
- 本附加说明的性质：固定于进程生命周期、无占位符残留、**只从启动时已校验的部署配置渲染**，
  不含用户、记忆、工具结果或请求数据。它是继模块级常量与时钟片段之后的**第三类来源**，
  需要独立的 D 记录，且不得被当作 D-114 例外的延伸。
- 与模块级常量一样，拼接时不做格式化之外的插值。

### 4.5 接线点

| 位置 | 改动 |
|---|---|
| [core/sender.py](../../src/raricy_bot/core/sender.py) | 脱敏 + 截断两行换成 `prepare_outbound(...)` |
| [comments/sender.py](../../src/raricy_bot/comments/sender.py) | `_prepare_content` 换成 `prepare_outbound(...)` |
| [app.py](../../src/raricy_bot/app.py) | render 提前到 `_auto_capture_answer` **之前**；**首次 render 后显式判空**（见下）；`send_text` 基于已 render 的正文；`append_exchange` 提交已 render、**不含披露**的正文 |
| [app.py](../../src/raricy_bot/app.py) 与 [comments/service.py](../../src/raricy_bot/comments/service.py) | 追加表情 addendum；评论的**无 `ContextManager` 回退分支**必须单独补，该分支不走 `build_messages` |
| [logging_setup.py](../../src/raricy_bot/logging_setup.py) | `FIELD_KINDS` 登记新字段 |

**聊天侧必须在归一之后立刻判空，否则会发出只有披露的回复。** 按上面的顺序，
空回答还会流进 `_auto_capture_answer`：自动记忆写入成功时它返回 `body + disclosure`，
`body` 为空串而披露非空，于是**最终发出一条只含记忆披露的回复**，同时向历史提交一条
空的 assistant 轮次——两者都违背本节承诺。现有代码也帮不上忙：`delivered=False` 且
`reason="failed"` 时 [app.py](../../src/raricy_bot/app.py) 的收口分支什么也不做
（`_note_forbidden` 只认 `forbidden` / `csrf`），并不会自动发失败通知。

因此：首次归一后若正文判空，**复查 generation**，然后调用既有的
`_notify_failure()` 并结束——不提取记忆、不发送、不提交历史。
`_notify_failure()` 走 `kind="notice"`、受 (频道, 触发者) 冷却、并占用一次通知额度，
所以这一轮**可能一个字节都不发**（冷却命中时）。这是有意的取舍：
宁可静默，也不能发出只有披露的正文或写入空的历史轮次。

**两条链路的历史行为不同，这是本设计最容易被漏掉的地方：**

- **评论**的短期历史写的是 Sender 实际发布的正文
  （`_published_text()`，见 [comments/service.py](../../src/raricy_bot/comments/service.py)），
  所以把 render 挂进 `_prepare_content` 就**自动**修好了历史。
- **聊天**的短期历史写的是**模型原文**，因为要发出的文本里含记忆披露，而披露绝不进历史。
  **只在 Sender 修会让历史留下未修正的坏 token，下一轮模型会模仿自己。**
  所以 render 必须提前到 `_auto_capture_answer` 之前，让历史拿到「已归一、无披露」的正文，
  两条红线同时守住。

预算与顺序约束：

- 附加说明由 [context.py](../../src/raricy_bot/core/context.py) 与 system 分别估算，
  **自动计入** `context_input_tokens`，需要有测试钉住。
- 时间片段仍必须是 system 的最后一段（D-114 第 2 条），表情附加说明排在其前。
- 聊天披露路径的 `growth` 现在要覆盖**脱敏增长与 render 增长**两件事。

### 4.6 日志

新增 `sticker.render` 事件，字段 `candidates` / `kept` / `fixed` / `dropped`，
类型均为 `TOKEN`（整数）。四者满足 `candidates == kept + fixed + dropped`，
即每个被识别为表情候选的 token 恰好计入一类，互斥且完备。
**不记正文，也不记具体名字**（名字属于模型生成的正文）。

## 5. 失败模式

| 场景 | 行为 |
|---|---|
| 名字不在清单 | 候选整段剥除，其余正文照发 |
| 格式写错但可归一出清单内名字 | 重写为规范 token |
| 格式写错且归一无果 | 剥除 |
| 超出 30 个 | 只留前 30 个 |
| 归一后命中敏感串 | 整枚丢弃（§4.1），不回填 `[redacted]` |
| 截断点落在 token 或代码区内部 | 回退到该区间起点（§4.1） |
| 正文超过 `max_chars` | 截断并使最终长度 ≤ `max_chars`，包含截断提示在内 |
| 模型整条回复就是一个非法 token | render 后为空：聊天侧**显式判空**后走 `_notify_failure()` 结束，不提取记忆、不发正文、不写历史（D-22）；评论侧预留**恰好释放一次**，不能声称「从未预留」 |
| 配置里合法但素材已下线 | 站点显示原文，本地无从察觉（§6） |

## 6. 已知限制

- **不访问清单接口**，因此只能保证配置中的名称与格式合法，
  **不能保证素材仍在线**。「读者永远看不到字面量」应读作
  「清除本地可识别的非法表情候选」。
- 别名表首版为空，只靠名称精确匹配；别名按实际观察到的错法再逐条补。
- 不做模糊纠正，因此「接近但没记准」的名字会被剥除而不是救回。
  若日后要加，必须限制输入长度、候选规模与短名称，并有独立开关。

## 7. 测试

新增 `tests/test_stickers.py` 与 `tests/test_outbound.py`，先写失败用例。

**判定与扫描**：全角括号、候选内多余空格、缺 `@`、别名命中、未命中剥除、
内容引用（四种长度）不受影响、Markdown 链接与嵌套括号不被错误替换、
归一后名称碰撞、第 30 / 31 个表情、代码块多反引号、`~~~` 围栏、
**未闭合围栏**、**未配对单个反引号不产生代码区**。

**敏感串复检**：`[@14/上 班]` 且「上班」是登记敏感串 → 整枚丢弃，正文不得出现该串；
token 之外的正文仍按第 1 步脱敏；命中时不回填 `[redacted]`。

**预算**：**无表情的纯超长正文**（没有 token 可增长时也必须 ≤ `max_chars`）、
归一增长导致超限、`max_chars` 恰好等于 `len(TRUNCATION_SUFFIX)` 与更小的预算、
`max_chars < 1`、未超限时不追加提示、最终长度含提示在内 ≤ `max_chars`。
其中「5001 字符 / limit 5000」是既有的 5012 越界用例，必须在改动后回落到上限内。
`tests/test_text_utils.py` 现有的 5 个截断用例是本改动的护栏，必须原样通过。

**切点与区间回退**：硬切落在 token 内部（残片与末尾隔着截断提示）、
硬切落在代码区内部（关闭反引号恰好被切掉，此时受保护的非法 token 不得暴露、
合法名字不得反过来渲染成表情）、回退后长度仍 ≤ `max_chars`、
回退不会误伤无斜杠的内容引用。`truncate_at_paragraph` 的既有调用点行为不变。

**幂等**：render 跑两遍逐字节相同、披露预算含 render 增长、
附加说明计入 `context_input_tokens`。

**配置**：`collection` 非 `"14"`、名称超长、名称含 `_`、名称含空白、重名、别名撞名，
全部启动失败。

**集成**：评论外部预留释放路径恰好一次、聊天历史提交的是归一后且不含披露的正文、
评论历史自动跟随发布正文、`enabled: false` 时正文逐字不变且无新增提示词
（脱敏与长度限制照常执行）、时间片段仍在 system 最后一段；
聊天侧归一后判空在**自动记忆开启与关闭两种配置**下都不发正文、不提取记忆、不写历史，
且冷却未命中时发出的是 `FAILURE_NOTICE_TEXT`。
