# 使用指南（站内用户）

本文件写给**在站内跟这台机器人打交道的人**（大区、私聊、博客评论区）。分两部分：第一部分（第 1 至 8 节）
是可直接发布到站点的说明，第二部分给维护与发布的人看，列了每条说法的代码依据与已知的口径出入。

文中 `<机器人用户名>` 指这台机器人在站点上注册的账号名，发布时替换成真实名字。

---

## 第一部分：发布稿

### 1. 我是谁

我是聪明山（raricy.com）的站内聊天与博客评论机器人，用一个普通的核心用户（core）
账号运行，走的是和大家一样的公开接口。

- **我不是真人，发言也不代表站方立场。**
- 站内的事可以问我：各模块怎么用、角色与权限、小鱼干与签到、内容引用语法、指南在哪。
- 我的回复总是引用触发它的那条消息，所以你能看清我在答哪一句。
- 你发给我的内容会转交给第三方模型处理，请不要发密码、密钥、验证码一类的敏感信息（见第 7 节）。

### 2. 怎么叫我

| 场合 | 怎么触发 |
|------|----------|
| 大区 | **每次都要精确 @** `<机器人用户名>`。区分大小写，且 @ 后面不能紧跟字母、数字、下划线或连字符——`@<机器人用户名>x` 不算叫我 |
| 私聊 | 直接发消息就行，不用 @（习惯性 @ 一下也没关系，我会去掉再处理） |
| 博客评论区 | 第一次要**精确 @** `<机器人用户名>`（规则同上）；我回复之后，**直接回复（引用）我的评论**就能继续，不用再 @ |

**一段对话怎么算：**

- 大区里想接上同一段，要**回复（引用）这段里的消息**再 @ 我；只 @ 不回复，等于开一段新对话。
- 同一段里的人共享最近**约十轮**上下文，我会用发言者标签分清谁说了什么；私聊按会话算，博客区按首次 @ 我的那条评论算。
- 对话归属过期后（大区与私聊 7 天、博客区 30 天），再回复我的旧消息会另开一段。
- 除了上表的两种触发方式，别的话我不会接——既不回复，也不会主动插话。

### 3. 命令手册

命令都由本地识别，位置不对就只是普通文字。几条通用规则：

- 命令**只在私聊与大区**解析；博客评论区不认（评论区里只有 `/help` 与 `/reset` 有效）。
- **一条消息里只能有一条命令**，且必须写在消息开头（大区里是去掉精确 @ 之后的开头）。
  命令后面紧跟着另一条命令时，我会回一句提示，请你分成两条消息发。
- 参数留空会返回**用法提示**，本地回复、不调模型。

#### 3.1 `/help` 与 `/reset`

| 命令 | 作用 |
|------|------|
| `/help` | 再看一遍我的能力、隐私与限制说明（**本地回复，不调用模型**） |
| `/reset` | 开始一段新对话，从头开始（旧的还在，别人仍可以接着旧的那段聊） |

这两条要求**整条消息就是命令**（前后不要带别的字），大小写不敏感。评论区里写
`@<机器人用户名> /help`，或直接回复我的评论写 `/help`、`/reset`，效果一样。
`/reset` 只作废短对话的上下文，**不等于删除长期记忆**（见 3.3）。
私聊重置还会作废旧轮次尚未发送的回答和相关提示；已经开始发送的站点请求可能完成，
重置不会撤回已发送的消息。

#### 3.2 六条能力命令

| 命令 | 查什么 | 前提 |
|------|--------|------|
| `/search <问题>` | 联网搜索（第三方 Exa） | 站长启用 MCP |
| `/fetch <网页URL> [要求]` | 读取一个网页，结果最多 5000 字符（第三方 Exa） | 站长启用 fetch 与 Exa |
| `/zhihu <问题>` | 知乎站内内容 | 站长启用 |
| `/map <问题>` | 高德的地点、坐标与天气 | 站长启用 |
| `/wolfram <问题>` | Wolfram 计算或事实查询 | 站长启用 |
| `/kb <问题>` | 站长放在本机知识库里的 Markdown 资料 | 站长启用；默认只对指定的私聊用户开放 |

- 用法是命令加空格加问题；`/searching`、`/kbase` 这类写法不会触发。
- 这六条**只授权当前这一轮**：由模型判断本轮要不要真的去查，一次一轮；`/search` 默认最多五条摘要。
- `/fetch` 每轮最多读取一个 HTTP(S) URL，完整工具结果最多 5000 字符，含标题、URL 和截断提示；
  配置的 token 预算可进一步缩短。网页正文只用于本轮，之后保留压缩摘要。
- 它们返回的都是**不可信的外部资料**，可能不准确或包含误导性文字；搜索只看摘要，不抓取网页全文。
- `/kb` **不联网**：只查站长放进知识库目录里的资料。没有命中我会直接说明，不会拿常识冒充资料，
  也不会因此转去联网；知识库有刷新周期，刚放进目录的文件可能要等一会儿才能检索到。
- 站长没启用 `/zhihu`、`/map`、`/wolfram` 时，我会回一句「暂不可用」；`/search` 与普通聊天不受影响。
- **评论区不支持这六条**，也不会因此调用搜索、网页读取、地图或读取知识库。

#### 3.3 全局记忆管理： `/memory`（仅管理员私聊）

个人资料统一使用 [§3.5 `/persona`](#35-用户画像-persona)，旧个人记忆入口只返回画像说明。
全局记忆管理按 `memory.enabled`、接入名单和管理员名单授权，默认关闭；五条命令都仅供管理员在私聊执行。

| 命令 | 作用 |
|------|------|
| `/memory list` | 同时列出全部已生效记忆与待批准候选，分段标明状态；长列表分页发送 |
| `/memory suggest <内容>` | 调用模型起草一条候选，暂不生效 |
| `/memory approve <MC-ID>` | 批准已展示的候选，转为生效记忆 |
| `/memory reject <MC-ID>` | 丢弃候选，保留已生效记忆 |
| `/memory delete <GM-…>` | 删除已生效记忆 |

`/memory` 显示管理用法。候选只有批准后才参与回答；已生效记忆统一适用于获授权的私聊、大区和博客评论，
不再按频道划分。旧条目和候选继续保留，已有 ID 仍能用于审批、拒绝与删除。

管理与画像独立配置，关闭画像不取消全局记忆授权。普通用户不能查询候选或执行管理操作；
未批准的内容不会进入普通模型请求。参与回答的内容可能随请求交给模型，正文不写日志或 SQLite。

#### 3.4 `/image` 与 `/image edit`

明确触发上游安全拦截会永久禁用该用户的图像生成及编辑，文本聊天仍可使用。
重启或 `/reset` 不解除，需管理员按[部署指南](DEPLOYMENT.md#图像黑名单管理)手动解除。
普通参数、鉴权、限流或网络错误不会自动禁用。

完整版启用图像服务后，可在私聊或大区使用 `/image <图片描述>`，大区仍须精确 @ 机器人。
编辑用 `/image edit <修改描述>`，并附一张参考图、直接回复图片，或写 `[@<10位图片ID>]`。
参考图支持 PNG、JPEG、WebP，默认不超过 5 MiB；多图或不可访问的图会被拒绝。
只有明确使用 `edit` 才把参考图交给编辑接口，普通生成不读取附图。

生成与编辑共用全站滚动 24 小时最多 50 张额度，每次输出一张。描述及编辑参考图发往独立图像服务，
不携带聊天历史、记忆或知识库。结果作为附件回复，上传公开图床，知道直链的人可访问。
图片最多保留 14 天；50 MB 空间不足时，先删除本功能最旧图，因此可能提前失效。
新图片默认请求低质量，上传前转为最长边不超过 1024 像素的 WebP，起始编码质量 90，
超限再调整，严格小于 200,000 字节；上传时关闭网站二次压缩。
仍有效且未开始删除的旧 7 天图片延长至原上传时间后 14 天，不重新编码；过期或已删除的图片不恢复。
到期每 10 分钟维护，停机或删除失败会延迟失效。
到期由机器人每 10 分钟检查并软删除，停机和站点缓存会影响实际失效时间。
未知结果不自动重试，可能继续占额度；上传或发送失败不退还已生成额度。
Light 暂不提供此功能。私聊 `/reset` 阻止尚未开始上传或发送的旧任务，不能撤回已完成的请求。

维护者待验收：管理员已配置第三方模型与密钥，诊断已确认其生成接口可返回 Base64 图片；
更新后的生产容器已直连生图成功；编辑的真实接口调用与站内图床显示尚待验收，见 [事件三](INCIDENTS.md)。
离线测试覆盖两条链路及额度、清理边界。

#### 3.5 用户画像 `/persona`

Linux 完整版由站长启用 `persona.enabled` 后可用，访问名单沿用记忆门禁。
管理操作均在你与机器人的私聊中执行；Light 暂未提供。

| 命令 | 作用 |
|---|---|
| `/persona` | 查看当前画像；尚未建档时启动访谈；有待办时继续审查 |
| `/persona on` | 开启已有画像的使用和自动更新；没有画像时开始建档 |
| `/persona off` | 停止使用和自动更新，结束待办，并撤回公开副本；私有画像保留 |
| `/persona edit` | 开始手动编辑流程，保留旧版本直到新版本确认 |
| `/persona answer <编号> <回答>` | 回答指定问题，也可按问题提示一次提交编号答案 |
| `/persona revise <修改意见>` | 修改当前草稿，每次建档或编辑仅允许一次 |
| `/persona confirm <草稿编号>` | 同意并保存你已收到的当前草稿 |
| `/persona cancel` | 取消待办流程，保留已生效画像 |
| `/persona public` | 预览准备公开的短文，确认后才发布 |
| `/persona private` | 撤回公开快照，保留私有画像 |
| `/persona clear` | 预览清空操作，确认后撤回公开并清除画像 |

首次建档会先说明资料用途，再读取最近 5 篇你本人可访问的博客，以及这个私聊中最近 50 条
你本人发送的有效文字。采样不包含机器人回复、系统消息、已删除消息、命令或纯图片；
资料不足按实际数量继续。资料与答案会发送给当前模型服务。

机器人根据已知资料提出 5 个问题。按编号作答，或直接回复问题消息；普通聊天不会自动作为答案。
随后审查一段短文，可提交一次修改意见，再确认草稿编号。只有已经送达的确切版本可以保存，
发送失败可重试。修改请求受理后，即使模型失败也只能重试同一修改意见，不能更换输入恢复额度。
每次回答或修改意见最多 1000 字，超限会提示缩短，不截取后保存。
下一次需要调整时重新使用 `/persona edit`。待办默认 24 小时过期，重启与 `/reset` 不重置修改额度。

确认后的画像默认私有，只在本人私聊中参考。知识水平按具体领域描述，兴趣、表达偏好和思维倾向
依据自述或已有资料推测；你可以纠正这些判断。手动修改的特征会锁定，后续自动更新保留。
普通私聊的机器人回复送达后才记录更新候选，默认累计 10 条、至少间隔 30 分钟、每个 UTC+8 日最多 6 次。
信息不完整也会继续生成或更新画像，不要求来源数量或跨日期；没有信息的维度留空，不编造内容。
全部没有可用信息时，短文说明各项待补充。
自动更新暂时失败不会改变已确认版本。

公开操作另行预览并确认，只发布短文，不公开问题、答案或证据。公开快照可以在大区或评论的相关
对话中使用，私有更新不会同步到它。关闭会撤回公开，重新开启仍保持私有；撤回未完成时会明确提示。
清空后保留无正文的迁移标记，旧个人记忆不会重新被读取。

问题、答案、压缩观察与草稿按本次流程授权暂存私有 Markdown；原始博客与私聊样本只在内存处理。
正式画像、控制状态和公开快照也保存在记忆目录，不把这些正文写入日志或 SQLite。

### 4. 我会自动读什么

不用下命令，下面这些我会在需要时自己读：

- **当前时间**：每轮我都会带上**服务器时钟**的当前时间，固定按 **UTC+8** 换算，与站内日历是同一个刻度，
  所以问「今天星期几」「现在几点」我能直接答。这只是让我知道「现在」，不会带来定时发帖、提醒之类的行动能力。
- **你回复的那条消息**：它带的引用与正文会一起看。被引用的消息若是图片，我会去读**那张缩略图**
  （站点只提供缩略图，分辨率比原图低，图里的小字可能读不清）；取不到时我会记下「图片未提供」
  并照常回答，已删除的引用不会去读它的图。
- **正文里的 `[@<内容ID>]`**：按长度识别并展开——8 位是**云剪贴板**（读正文，单条最多 2000 字，
  超出部分不取）、9 位是**投票**（读标题、选项与票数）、10 位是**图床图片**（站长配了能看图的
  模型时我能看到图，否则只知道那里有一张图）。剪贴板与投票要么是公开内容、要么你自己是作者，
  否则读不到：那时我会写下「加载失败」，而不是装作那段不存在。写在**代码块或行内代码**里的
  `[@id]` 一律不展开；你回复的那条消息里若有引用，我会连它一起读。
- **你引用的博客**：我会去读它的**标题与正文**。正文超过 1000 字（站长配置）时只拿到标题，
  并会明确写下正文没给；取不到（已删除、暂时读不到）时同样只有标题。没被引用的博客我不会主动去看。
- **博客评论区的每一轮**：会读文章标题；正文不超过 1000 字时可能随本轮一起提供，超过则不提供。
  正文里写的 `[@id]` 同样会展开。
- **图片**：取决于站长有没有给我配能看图的模型。配了，你**这一轮**发的图会随本轮交给第三方模型
  （更早轮次里的图看不到）；没配，我会明确告诉你图没读到，请改用文字描述。评论区一轮最多几张图
  由站长定（默认 3 张），按「你的附件 → 评论正文里引用的图 → 文章正文里的图」的顺序给；
  **引用其他博客的附件我一直读不了**。评论区里**只发图、不写字**只能以「直接回复我的评论」
  的形式出现（第一次叫我必须 @，而 @ 需要文字）。
- **大区里最近的公开文字消息**：为了理解正在发生的讨论，我会在内存里保留最近 50 条大区文字消息、
  每条最多前 500 字。你叫我时，其中装得下的那部分会随这一轮一起发给第三方模型——**你没 @ 我的
  公开发言也可能被交给模型**。图片和拍一拍不进入这份内容；它只在内存里、只用一轮，用过即删除，
  重启也会丢失。这份内容是全大区共用的，所以别段的公开文字同样可能被读到。

### 5. 我做不到什么

- **普通聊天不联网，也不能运行代码。** 联网只有 `/search`（以及站长启用的那几条能力命令）
  这一条路，而且只授权当前一轮。
- **查不到站内数据**：别人的余额、鱼干流水、通知、申诉进度、资料，都要你自己去对应页面看。
- **不能替站方办事**：解禁、恢复内容、改角色、发邀请码、裁决申诉，一律请走 `/contact` 或 `/audit`。
- **长期记忆默认没有**：短对话的上下文只放在内存里，换一段对话就是重新开始，服务重启也会丢
  （去重与额度状态会保留）。你主动确认的用户画像与旧记忆另存 Markdown，参见 §3.3–§3.5。
- 不确定的事我会直说，不会编。站内规则以页面为准，指南在 `/clipboard/guide`、
  `/image/guide`、`/vote/guide`、`/tool/cattca-guide`。

### 6. 为什么有时不回、有时很慢

| 现象 | 原因 |
|------|------|
| 大区里没 @ 我 | 设计如此：只回应精确 @，否则会把当天的额度烧光 |
| @ 了我，却像没接上文 | 没有回复链内的消息就会开一段新对话；想接上就回复这段里的消息再 @ 我 |
| 博客区 @ 了我却迟迟没反应 | 评论每 30 秒扫一次全站最近 100 条，通常半分钟到一分钟内开始处理；启用功能之前的旧评论、两次轮询之间新增超过 100 条的窗口外评论，可能漏失 |
| 博客区只是普通评论、或回复了别人的评论 | 设计如此：只回应首次精确 @ 和直接回复我的评论，否则会把当天的评论额度烧光 |
| 博客区里模型失败或额度用完 | 评论区是**静默**的：忙碌、失败、额度用尽都不会发提示，只是不回 |
| 一段时间完全不回 | 多半是 24 小时滚动额度用满，或者排队积压；账号被禁言也会全站静默 |
| 只回了一句固定话 | 比如「消息太长」「这张图片我没能读取」「你引用的这篇博客我没能读取」「我暂时不能查看博客内容」「没有找到相关资料」，按那句话的提示改一下再发 |
| `/kb` 说没找到资料 | 检索只在当前已建立的索引里做，资料不足时我不会硬答；换个说法，或去掉 `/kb` 直接提问 |
| 命令没生效 | 命令必须在消息开头、且一条消息只能有一条；`/kb` 还可能因为没权限或索引未就绪而回提示 |
| `/zhihu`、`/map`、`/wolfram` 说暂不可用 | 站长没启用这三个能力，或对应的密钥没配好。`/search` 与普通聊天不受影响 |
| 回复很慢 | 模型在生成；超时上限是 45 秒，超过就判定失败 |
| 回复中途停住 | 模型侧的输出长度上限，偶尔会在句子中间截断，再问一次或让我接着说 |
| 回复末尾写着「（内容过长，已截断）」 | 这条太长，被按自然段截断了 |
| 短时间内反复问，却不再收到任何提示 | 主动提示（忙碌 / 失败 / 额度）对**同一个人**每 5 分钟最多一条；别人不受影响。额度彻底用尽后我会完全静默 |

额度是**滚动的 24 小时窗口**（不是自然日归零）：用满后不再回答，随着窗口滑过去会逐渐恢复。

### 7. 隐私：关于你的消息

- **你发给我的内容会被转交给第三方模型服务处理**，这是我能工作的前提。请不要发密码、密钥、
  身份证件一类的敏感信息。
- **只有你明确使用能力命令时，当前轮的问题才会流向对应的第三方**：`/search` 交给第三方 Exa
  搜索，`/fetch` 将 URL 交给 Exa 读取网页，`/zhihu` 交给知乎，`/map` 交给高德，`/wolfram` 交给 Wolfram。它们各自返回的都是
  不可信资料，可能不准确或包含误导性文字。
- **`/kb` 是另一条边界**：它读的是站长放在本机的知识库，命中的片段随本轮问题一起交给第三方
  模型，但**不会**发往任何搜索上游；反过来，普通聊天也不会自动去读知识库。知识库里的内容同样
  是不可信资料，其中的任何「指令」都不作数。
- 各家 API Key 只由服务运维通过环境变量提供，不会写进消息、配置文件或公开内容；评论区不会使用它们。
- **在博客评论区**：评论正文、文章标题、不超过 1000 字的文章正文都可能发送给第三方模型；
  文章超过 1000 字时不发送正文。评论本来就是公开的，请只发你希望公开的内容。
- **程序这边不把消息正文写进日志或数据库**：日志里只有消息 id、频道、结果这类状态字段；
  数据库只存运行状态（去重、水位、发送记录）。
- **用户画像需本人启动与确认**：`/persona` 会读取本人博客及当前私聊样本并交给模型，
  问答、压缩观察和草稿暂存私有 Markdown；确认后保存短文与特征，随普通私聊自动更新。
  查看与修改用 `/persona`、`/persona edit`，暂停用 `/persona off`，删除用 `/persona clear`。
  公开需单独确认快照，关闭会撤回；细节见 §3.5。
- **公开画像是本人确认的快照**：使用 `/persona public` 预览并确认后，公开对话中出现或精确提到你时，画像短文可能随请求交给模型。撤回用 `/persona private`；`/persona off` 也会撤回。公开请求只读公开目录，详情见 §3.5。
- **大区里别人加入你那段对话时，这段里近期的聊天记录会再次发送给模型**；大区里最近的公开文字
  消息同样可能被交给模型（细节见第 4 节）。这些内容本来就发在公开大区里，但请注意这一点。
- 对话归属（谁回复了哪条）会保留 7 天，博客区保留 30 天。
- **在博客区，每条成功的评论回复都会真实通知被回复的人**——评论写入就会通知，没有机器人豁免。
- 站点侧的聊天消息按站点自己的规则保存（软删除），那部分与这台机器人无关。

   但用户看到的那句话仍是旧文案。
2. **输入长度那道闸实际碰不到**：本地限制是 8000 字符，而站点侧的聊天消息上限是 **5000 字**
   （纯文本与带附件同值，见 `docs/materials/chat-bot.md` §7.1 的长度上限表），超过 5000 的消息
   在站点侧就发不出来，所以 `TOO_LONG_TEXT` 在正常使用中不会出现。真正会遇到的是模型侧输出上限
   导致的截断。
3. **模型侧截断没有任何提示**：`model.max_output_tokens`（默认 600）触发的截断不会追加说明，
   回复会在句子中间停住；只有本地那层 5000 字符的截断会写「（内容过长，已截断）」。
   嫌难看就调大 `max_output_tokens`，详见 `DEPLOYMENT.md` §15.1。
4. **评论区的"漏失窗口"是上游限制**：发现靠每 30 秒拉一次全站最近 100 条，两次轮询之间新增
   超过 100 条时窗口外评论无法恢复。发布稿已如实写"可能漏失"，没有承诺必达。
5. **评论区的额度文案**：聊天区的 `QUOTA_NOTICE_TEXT` 写「请明天再来」，实现是滚动 24 小时窗口；
   评论区额度用尽则完全静默，连这句话也没有。发布稿对两处都按实现口径描述。
6. **公开条目的命中还取决于站点的用户查询**：普通用户名、博客与文章正文、剪贴板里的用户名
   都要过一次 `GET /api/chat/users` 的精确核对（完整用户名、大小写敏感）。这个接口站点限频
   20 次/分钟，机器人自己节流到 15 次/分钟并做正/负缓存；限频、超时或响应形状认不出来时按
   「这个人对不上」处理（fail-closed），那一轮就不会用到对应的公开条目。发布稿与 `/help` 都用
   「可能」描述这件事，没有承诺必中——本文件也不要写成「提到就一定用上」。
7. **自动提取的披露可能缺席（唯一一处「写了但没说」）**：站长的 `behavior.max_output_chars`
   紧到装不下「披露 + 一个回答字符 + 截断后缀」时，这一轮的回答照常完整发送，但末尾**不会**有
   「（已新增私有记忆 UM-……）」那句。兼容旧条目仍写入敏感 Markdown，需由运维核对；旧个人查询入口已退役。
   服务端会记一条 `reason=disclosure_no_room` 的日志（D-77）。因此**发布稿不要把
   自动记忆写成「每次保存都会告诉你」**：正常情况下会在回答末尾说明（这是设计的要求），但这是
   一条有例外的承诺。部署侧给这两个上限留余量即可让它在默认配置下永远不出现。

### 2.4 定时发文（维护者）

这一节**只面向部署者**。定时发文不是聊天命令：用户在聊天里敲不出它，`/help` 里也不会出现
它（`capabilities.blog_write` 的 `command` 是 `None`，`CAPABILITY_COMMANDS` 会把它过滤掉），
所以第一部分没有对应条目。

发文走普通用户网页表单同一个 `POST /api/blogs`，接口依据是站方
[blog-bot.md](../materials/blog-bot.md)，现行边界见 D-106、D-157。
它是 core+ 功能，账号掉出核心用户即整体失效。定时任务显式以 `internal` 发布，
即仅站内可见；当前任务配置不提供 `link` / `public` 的切换。

#### 启用

`config.example.yaml` 的 `blog` 段默认整段关闭。任务的数量与字段都在 YAML 里，
**没有 Web 界面**：改动走版本控制。`prompt` 与 `drafts_dir` 必须恰好给一个；
`name` 是持久标识，**改名等同新建一个任务**（旧任务的历史记录不会被继承，
同一个调度点会按新名字重新领取）。`drafts_dir` 的相对路径以**配置文件所在目录**为基准 ——
容器里配置在 `/app/config.yaml`，所以 `./drafts` 指 `/app/drafts`，`docker-compose.yml` 已按
`knowledge` 同样方式只读挂载它（宿主目录要先存在，否则 Docker 建成 root 属主、容器读不到）。
**漏挂不报错**：目录不存在等同队列空，表现只是每次到点记一条 `blog.empty_queue`，
日志看着正常而文章永远发不出去。

维护者可用 core+ 会话查询站方 `GET /api/categories`，从实际清单选数字 `id` 填入
`category_id`，并检查有效的 `admin_only_posting`；不能把栏目名称、slug 或 path 当成 ID。
留空发为「未分类」。机器人运行期不自动选择栏目，栏目由维护者配置。

#### 调度行为

- 调度点按**固定 UTC+8** 解释，不跟服务器时区；本地日预算同样按 UTC+8 零点切，
  与站方 `dayStart` 同口径。
- 进程**启动时只处理当前分钟**的调度点，不追补停机期间更早的点。正常运行按
  `(上次扫描时间, now]` 枚举，且下界再收紧到 `now - 5 分钟`。
  **停机一整天后不会一次性冒出几十篇文章。**
- **`blog.misfire` 的触发条件要看清**：它只在**本次扫描确实跳过了落在枚举窗口内的点**时才记。
  启动那一支看的是「当前分钟开头往前 5 分钟」这一段，所以：
  - 启动落在有调度点的分钟上（例如 09:00:30 启动、任务排在 09:00）→ **不记**，那个点正常领取；
  - 09:02:30 才启动、任务排在 09:00 → 09:00 落在查询窗口内 → **记一条**；
  - **09:10 才启动、任务排在 09:00 → 不记**。这个点确实被跳过了，但它已经在 5 分钟窗口之外，
    而判断「它是被跳过、还是上一轮已经发过」需要持久化的扫描时刻，首版没有。
  也就是说：**日志在，说明刚错过；日志不在，不代表没错过。** 长时间停机后某个调度点没发出去、
  而日志里什么都没有，这是预期行为，不是故障。要确认某天该发的到底发了没有，
  去看 `blog_runs` 里那一行在不在、是什么状态，别依赖这条日志。
- 已经领取但超过 5 分钟还没开始的执行会转成 `skipped`，`reason=misfire`。
  已经开始的任务允许跨分钟完成。
- `tier: must` 到点必发起；`tier: maybe` 到点**掷一次骰**并把结果落库 ——
  未中签的执行重启后不会被重新掷一次。`must` 同样服从日预算。
- 稿库按**文件名升序**取第一篇可投递的稿件；队列为空时 `must` 记一条 WARNING。
  单个文件解析失败不会堵住队列，会跳到下一个。

#### 生成侧

- 一次生成最多调用**一个**工具（复用 `mcp.features.blog_write` 的白名单与
  `max_tool_calls_per_turn`），**没有**多步研究循环。
- 整次生成（含等待模型并发门、工具执行与两次模型请求）上限 180 秒。
- 输入侧受 `behavior.context_input_tokens` 约束：工具结果加上写作要求装不下时**直接失败**，
  不会丢弃写作要求硬发。输出侧用 `model.max_output_tokens`。
- 模型因 token 上限被截断（`finish_reason=length`）、拒答或超时都算生成失败：
  **不会**发出半篇文章。
- **取材失败会静默降级**：`blog_write` 的六个绑定里**只要有一个**上游服务器不可达、
  工具没被发现，这一轮就整体退回「无工具生成」——文章照写，只是没有取材。
  这件事**只在 DEBUG 级别有记录**，INFO 及以上看不出来。所以「文章质量突然变差、
  但日志一切正常」的第一嫌疑是某个 MCP 服务器掉了：查 DEBUG 日志，或看启动期的 MCP 日志。
  默认六个绑定意味着这条降级的门槛不低，把不用的工具从 `bindings` 里去掉可以降低它。

#### 结果不确定时会发生什么（这是本功能最需要维护者理解的一点）

站方**没有幂等键**，所以「POST 已经发出、结果没读到」是一个本地无法消除的状态。
本地不承诺 exactly-once，也**不承诺必达** —— 它承诺的是**不重复发布**：

- 超时、网络错误、5xx、读不懂的响应、成功但缺少合法文章 id、POST 期间被取消，
  一律记成 `unconfirmed`，**继续占着当天的额度**，只做只读对账，**绝不自动重投**。
- 只读对账每 5 分钟跑一次，每轮最多 10 条、单条最多查 5 页（每页 50 条）、
  最多读 10 篇候选正文。只有「完整走完这一轮搜索、且恰好命中一篇作者 id、标题、正文指纹
  全部一致的文章」才会补记成已发布。
  **搜索为空不算「没发出去」**：搜索受栏目过滤，分页也会随并发更新移动。
- 单条累计查 12 次仍未确认就停止自动查询并告警，**继续保持 `unconfirmed` 与占额**。
- 结果不确定的行**跨 UTC+8 午夜持续占 1 篇额度**，不会在零点释放：
  零点一过就放额度，等于把「结果未知」当成「从未发生」，那正是重复发布的入口。
  日上限因此可能被一条查不实的记录长期压住。
- 确定失败会释放额度：站方明确拒绝（400/403/401）转 `rejected`；429 且是稿库来源、
  同指纹累计投递少于 3 次，转 `retry_wait`，**次日**在新调度点复用原投递行重试。
  现写稿不缓存到次日，429 直接转 `abandoned`。**只有确定的 429 才允许重试。**
- 每天最多记一条「预算耗尽」日志；预算耗尽只挡住生成与投递，**不挡住只读对账**。

#### 人工核实不确定的记录（首版唯一的手段）

首版**不提供**自动解锁的聊天命令或模型工具，也不按年龄删除记录（删掉记录会让同一篇文
重新发布）。核实需要站方事实，步骤是：

1. 先关闭发文（`blog.enabled: false`）并重启，让本子域停止领取与投递；
2. **备份 SQLite**（`storage.db_path` 指向的文件，连同 `-wal`/`-shm`）；
3. 按 `(site_base_url, self_user_id, id)` 定位 `blog_posts` 里的那一行
   （`status = 'unconfirmed'`，`content_hash` 就是它的内容身份）；
4. 到站点上确认事实：
   - **确认已经发出**：核对作者是机器人账号、标题与正文指纹与本地 `content_hash` 一致，
     然后补上站方的 `site_blog_id`、把状态改成 `published`、按规则补齐计费区间；
   - **确认没有发出**：才可以把状态改成 `rejected` 或 `abandoned`，并**同时**清空本次计费区间，
     额度才会释放；
   - **核不实**：保持 `unconfirmed`。继续占额是代价，重发一篇已经存在的文章是事故。
5. 任何人工状态改动都必须在**一个事务里同时**更新投递状态、计费区间与关联的执行记录，
   只改一半会让预算账与实际发出对不上。

**不要在不确定记录上直接手动调用发布接口。** 站方不知道你刚刚发过什么，
重复发布的后果由维护者承担。

#### 被拒绝的记录（`rejected` / `abandoned`）怎么恢复

`unconfirmed` 之外还有一类会**永久**拦住一篇稿子：站方明确拒绝（401/403/400）记 `rejected`，
429 用尽次数或现写稿被限流记 `abandoned`。这两种是**确定没发出去**，额度已经释放，
但**同一个指纹不会再自动投递**（D-109）。最可能的真实触发是一场账号事故
（被禁言、core+ 短暂失效）把当时到点的稿子全部烧掉 —— 而且是永久的。

恢复办法与 `unconfirmed` 同一条纪律，但判据相反：这两种状态**本身就是「没发出去」的正向证据**。

1. 关闭发文并重启，**备份 SQLite**；
2. 按 `(site_base_url, self_user_id, id)` 找到那一行，确认 `status` 是 `rejected` 或 `abandoned`
   且 `site_blog_id` 为空；
3. 到站点上确认那篇文章**确实不存在**（按标题搜一次，注意搜索受栏目过滤，必要时翻页）；
4. 用 `DELETE` 删掉这一行，**或者**把 `content_hash` 保持不变、只把 `status` 改回 `retry_wait`
   并把 `retry_after_day` 设为今天 —— 两种都可以，前者等于「这篇稿子重新排队」，
   后者复用原行。**改状态与清空计费区间必须在同一个事务里**；
5. 重新启用发文。

只要第 3 步核不实（比如标题搜索空结果，但你不确定搜索能否覆盖到），就**别删**，
保持原状等人工判断 —— 与 `unconfirmed` 一样，宁可漏发。

#### 改稿子女件会绕过指纹去重

去重的身份是 **`(标题, 正文)`**（blog/codec.py 的指纹）。所以**编辑队列里的一篇稿件，
等于换了一篇新稿**：即使它前一版可能已经发出去过、或者正停在 `unconfirmed` 等确认，
改过的那一版也会拿到一个新指纹、作为新文章发出去。

这是内容去重的固有代价（正文不落库，就没法把「同一篇稿子的两个版本」关联起来），
但它是本功能最可能让运维**无意中发出两篇近似文章**的一条路。规矩很简单：
**一篇稿子投出去之后、在确认它的结局之前，不要改它。** 要改就先按上面两节把结局查清楚。

#### 启用前请做一次真实核对（`author_id`）

只读对账靠 `GET /api/blogs` 列表里的 **`author_id`** 字段做精确匹配（INTERFACES §53.10）。
这个字段名是照着固定提交的上游源码读出来的，**没有在本仓库的自动化测试里对着真实响应取过样**
（测试一律用替身）。如果上游实际给的是别的字段名，对账会**每一轮都失败**：

- 表现是每轮记一次 `reconcile_incomplete`，累计 12 次后按 `reconcile_exhausted` 告警，
  该行**永远停在 `unconfirmed` 并继续占额**；
- 这是**保守方向**：不会误确认、不会重投，但额度会被长期压住。

所以**第一次启用前**，用机器人账号发一次真实请求，确认列表每一项里确实有 `author_id`
（与 `id`、`title` 同级）。没有的话先别启用发文，把字段名反馈回来改 `site/client.py` 的解析。
**不要**为了让它跑通而退回用 `author` 用户名匹配：用户名可变，用它匹配可能把别人的文章
认成自己发的，那比不发严重得多。

同一次核对里请**顺手把这两件事也验了**，它们的失败方式和 `author_id` 一模一样（fail-closed、
占额、要等 12 轮才告警），而且同样只在真机上才看得出来：

1. **正文与标题能原样往返**：发一篇带前后空行、中文标点与 emoji 的测试文，
   再用 `GET /api/blogs?search=<标题>&search_fields=title` 找到它、取回正文，
   确认**逐字节**等于你发出去的那一份。指纹是对「发出去的字节」算的，
   站点若在写入或读取时做过任何归一化（trim、换行转换、实体转义），指纹就永远对不上，
   这篇记录会一直停在 `unconfirmed` 并占着额度。
2. **拒绝路径的信封形状**：故意用一次会被拒绝的请求（例如一个不存在的 `category_id`），
   确认返回的是**带 `code` 与字符串 `message` 的业务信封**、且 HTTP 状态码与 `code` 同值。
   这条决定了 `rejected` 能不能被正确识别 —— 认不出来的会被当成 `unconfirmed` 长期占额
   （保守但白占），而认成拒绝则会永久终结那个指纹（要按上一节人工恢复）。
3. **429 的信封**：如果能在测试期触发一次限流，确认 `code` 是 429。
   这是**唯一**会进入有界重试的确定结果，也是整个设计里唯一一条可能重复发布的路径
   （前提是站方在 429 之前其实已经建了文，见 D-106/D-109）。

#### 已知的取舍（发布前请留意）

- **不补发**停机期间错过的调度点；**不保存**现写稿正文，因此进程崩溃后无法恢复原稿 ——
  崩溃时已经走到「已预留、还没发出」的窗口也可能永久待确认。这是不保存正文又无站方
  幂等键时主动接受的代价，不是缺陷。
- **不承诺 exactly-once**：宁可漏发或等人工核实，也不用重复发布换成功率。
- 发布后**不再改文**：编辑文章的 `PUT /api/blogs/:id` 本功能不使用。
- 只允许**单实例**运行：两个机器人进程共享同一账号发文不受支持。
- **「预算耗尽」日志的去重只在本进程内**：日志目标为「每个账号每个 UTC+8 日最多一条」，
  而实现只在内存里记住今天是否已经记过（Store 没有为该日志去重提供持久位置）。因此**同一天里
  每重启一次，就可能多一条** `budget_exhausted` 日志。这是已知偏差，不是遗漏：
  它只影响日志条数，不影响任何预算判定。为它单开一张表属于扩大范围，首版不做。
- **任务改名或从配置里删掉**时，那条遗留的排队执行会以 `failed` 收尾、原因写成
  `interrupted`（日志事件是 `blog.task_missing`，能看出真实原因）。这是措辞上的偷懒：
  `interrupted` 严格说是「进程死在半路」。持久记录里的原因与日志事件对不上时，
  以日志为准。**不要**为了「清理」而删掉这些行 —— 删记录会让同一篇文重新发布。

### 2.5 改这份文档时注意

- 用户说明与 `texts.py` 的帮助、失败提示和记忆回执保持一致；聊天与评论的触发方式、能力范围分别核对。
- 记忆披露同时区分共同记忆、所属用户私有记忆和主动公开的个人条目；公开帮助文案以
  `texts._HELP_MEMORY_PUBLIC` 为准，改写时同步本手册与文案测试（INTERFACES §36、§50）。
- 长度、额度等可配置数字按默认值说明，不当作每个部署的实际值；实际帮助文案应注入配置。
- 行为变更先核对 INTERFACES 和相关 D 条目，再更新用户说明。关闭功能、软故障和已知例外也须如实披露。
- 设计稿归档后，未完成验收仍保留在本手册；不能因文档整理勾选尚未执行的验收项。
